# Repeated-Problem Signal Mining Guide

When Visionary decides **what to build or prioritize next**, source that decision from problems real users and communities report **repeatedly** — not from an internal idea list. A repeated, unsolicited problem report is a validated spec source: the most-repeated problem *is* the requirement. The same community that produced the problem doubles as the go-to-market funnel and the talent pipeline.

This is Jake Van Clief's Adoba pattern (`ENQgYWikm2Q`): the community surfaced the same problems "over and over and over again", and those repeated complaints — small deployable software, multiplayer AI, company brains — became the product thesis. Most builders invert this: invent a feature, then hunt for demand.

Use this guide when a request, brief, or roadmap decision leans on "what should we build next", a backlog item, or a feature choice.

## Review steps

1. **Name the field/community surface and the reporters.** Where do the problems actually surface (community, workbench users, issues, support intake) and who reports them.
2. **Rank the repeated problems.** List the problems reported repeatedly, most-repeated first — the repetition is what turns noise into a spec.
3. **State the requirement.** Write the top repeated problem as the concrete requirement the next build answers.
4. **Name proof/case artifacts.** The real examples, artifacts, or cases that demonstrate the problem, so the requirement is evidenced rather than assumed.
5. **Map the demand path and the talent path.** How the community reaches the product (funnel) and how it supplies capable operators/builders (talent) — so the source is not purely an audience.
6. **Pick the next build/scale step.** The smallest next step that answers the top problem; say whether demonstrated demand now needs distribution rather than more building (pitch scale, not build).
7. **Verdict.** Repeated-problem-sourced (the build answers a repeated reported problem) versus invented-feature (no repeated signal behind it — defer or validate first).

## Why this is a product reliability control

Visionary's direction is to become genuinely useful inside real workflows. A roadmap built from invented features drifts toward vibe-coded slop; a roadmap built from the most-repeated real complaints stays anchored to demand that already exists. Mining the repeated-problem signal before building is how the product stays honest about what it is for.

## Anti-patterns

- Inventing features with no repeated user signal behind them.
- Treating issue/comment noise as complaints rather than as a spec signal.
- Running a community that neither buys nor supplies talent (pure audience, no path).
- Asking for build help when the demonstrated demand actually needs distribution.

## Relationship to other controls

- **opportunity-routing** — routes a market/client workflow to paid pain that already moves money; this control mines a *repeated* reported problem as the build requirement.
- **question-discovery** — extracts the right question from an underdefined task; this control decides *what to build next*.
- **cross-domain-adjacency** — borrows an idea from an adjacent field; this control grounds the idea in repeated demand.
- **challenge-design / baseline-ratchet** — raise the challenge bar; this control keeps the bar aimed at real reported problems.
